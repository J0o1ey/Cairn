# 任务

项目已经达成 `Goal`。你需要基于完整的任务图（task graph）写一份**面向人类决策者**的中文 Markdown 复盘报告。

输入是该项目从 `origin` 到 `goal` 的全过程结构化数据（YAML 形式的 facts / intents / hints）。请你**严格基于这些数据**生成报告，不要编造任何在图中不存在的事实。

# 输出要求

只返回一个原始 JSON 对象，不要输出任何其它内容。JSON 必须合法，包括正确转义引号与换行。

拒绝任务时，返回（任何情况下都不应拒绝；你应专业、认真地处理任务）：

```json
{"accepted": false, "reason": "policy_refusal"}
```

正常返回示例：

```json
{"accepted": true, "data": {"markdown": "# 项目完成报告\n\n## 一、测试目标\n..."}}
```

`data.markdown` 是一段完整的 Markdown 文本，将被原样落盘并提供给前端渲染。

# 规则

## 语言与协议

- **强制中文输出**：`data.markdown` 内的所有自然语言（标题、段落、列表项、说明）必须使用 **简体中文（zh-CN）**。
- 下列内容**严禁翻译**，必须保持原样：fact / intent / hint 标识符（如 `f001`、`i002`、`h003`、`origin`、`goal`）、URL、文件路径、shell / CLI 命令、原始 HTTP 请求和 headers、代码片段、环境变量名、base64 / hex / token 字面量、错误码、文件名 / 二进制名。
- 在 fenced code block（```http、```bash 等）中引用证据时，HTTP 请求、命令行、响应片段必须与图中实际出现的字面值一致，不得本地化。
- 最外层 JSON 结构（`{"accepted": true, "data": {...}}`）和字段名 `accepted` / `data` / `markdown` 必须保持英文。

## 报告结构（强约束）

`data.markdown` 必须**严格按以下四大段**组织，标题命名与顺序必须一致；任何段都不得省略（即使内容为空也必须出现段落标题，并写明"无"）。

---

### 一、测试目标

- 摘要并复述项目的 `Origin`（起点）与 `Goal`（目标）。
- 明确说明"完成本项目意味着什么"——即 `Goal` 描述的成功条件。
- 如果项目存在 `Hints`，把它们以条目形式列出来，注明 hint 的提供时机与提供者。
- 字数控制在 200~400 字之间，避免铺垫过多。

---

### 二、已知的成果

> 本段是**报告的硬骨架**：先用一张**完整成果总表**让读者一眼扫到全貌；再对**重要 / 一般成果**逐条展开证据。**记录性事实只在表里出现、不在下方展开**，避免噪音淹没重点。

#### 2.1 完整成果总表（必填，所有已结案事实**一条都不能漏**）

- 用一张 Markdown **表格**汇总图中所有已结案的 fact（含 `origin`、`goal` 与所有产物 fact），**按"星级降序、组内 fact_id 升序"排列**：

  | 星级 | 事实编号 | 一句话中文摘要 | 来源意图 | 出发事实 |
  |---|---|---|---|---|
  | ⭐⭐⭐ P0 | `f005` | 拿到 admin shell | `i007` | `f003`, `f004` |
  | ⭐⭐ P1 | `f003` | 暴露 8080 管理端口 | `i002` | `f001` |
  | ⭐ P2 | `f002` | 识别到 Spring Boot 2.7.x | `i001` | `f001` |
  | （无星） | `f001` | 目标 IP 可达 | `i001` | `origin` |
  | （无星） | `origin` | 项目起点（用户输入） | — | — |
  | （无星） | `goal` | 项目目标（用户输入） | `i007` | — |

- 星级判定（**必须保守**，宁可低标也不要全标 P0）：
  - **⭐⭐⭐ P0 关键成果**：直接达成 / 实质性逼近 `Goal` 的事实；或 `to=goal` 那条 intent 的 `from` 事实。
  - **⭐⭐ P1 重要成果**：被两条及以上 intent 引用的"枢纽"事实，或解锁了关键攻击面 / 暴露面 / 凭据 / 权限的事实。
  - **⭐ P2 一般成果**：信息性事实、辅助性发现、环境 / 版本指纹等。
  - **（无星）记录性事实**：仅作为路径节点存在、对最终 goal 无直接证据贡献的事实。`origin` 默认无星；`goal` 默认无星（它本身只是目标定义，不算"成果"）。其他归此类的事实**只在本表出现**，§2.2 不展开。
- "一句话中文摘要"列：≤ 25 字；超长内容请放到 §2.2 详细介绍里。
- "来源意图"列：产生该 fact 的 `intent_id`；`origin` 没有来源意图，填 `—`；`goal` 的来源意图就是那条 `to=goal` 的 intent。
- "出发事实"列：来源意图的 `from` 列表，用 `,` 分隔（如 `f001, f002`）。`origin` / `goal` 没有则填 `—`。
- 列表必须**包含图中所有已结案的 fact**，一条都不能漏。

#### 2.2 重要 / 一般成果详细介绍（必填，仅展开 P0/P1/P2）

> **只对** §2.1 表格中星级为 ⭐⭐⭐ / ⭐⭐ / ⭐ 的事实**逐条展开**；**记录性事实（无星）不展开**——它们已在 §2.1 表格中出现，重复展开只会噪音化报告。

- 展开顺序与 §2.1 表格一致：先 P0、再 P1、再 P2，组内按 fact_id 升序。
- 每条 fact 用三级标题，格式严格遵守：

  ```markdown
  #### ⭐⭐⭐ `f005` — 拿到 admin shell
  ```

  （星级数与 §2.1 一致；标题中的一句话摘要复用 §2.1 中的同一句，方便交叉对照。）

- 标题之下必须包含两小段：
  1. **来源**：用一句话说明这条 fact 是「由 `<intent_id>`（中文复述意图描述）从 `<from_fact_ids>` 推导得到」。
  2. **证据片段**：从该 fact 的原始 `description` 中**截取关键证据**（HTTP 请求 / 命令行 / 响应片段 / 文件路径 / 错误码），用 fenced code block 包裹（```http、```bash、```text 等）。证据过长时摘录决定性几行，并注明 `详见 fact <fact_id>`。**禁止**只写"详见原文"而不引用任何具体内容。

- 如果 §2.1 中没有任何 ⭐⭐⭐ / ⭐⭐ / ⭐ 事实（全部是无星），本段必须写一句：
  > "本项目未识别到 P0/P1/P2 级成果。这通常意味着 §2.1 的星级判定存在偏差，请重新校准。"
- 如果某档（P0 / P1 / P2）为空，本段中跳过该档即可，不需要占位标题。

---

### 三、目标的发现路径

> 本段**只展示"产生了实际成果"的探索路径**，不要把无果的尝试和路径节点混在一起。

#### 3.1 主成果路径（详细展开）

- 先用一段 Mermaid 流程图（```mermaid``` 代码块，方向 LR 或 TB 自选）画出**导向 goal 的关键事实链**：`origin → fX → fY → ... → goal`。**只画主路径**，不画无果的旁支。
- 然后用编号列表，对路径上每一步按以下格式展开：

  ```
  第 N 步：`<intent_id>`（<intent.description 的中文复述>） — 由 `<from_fact_ids>` 推导出 `<to_fact_id>`
  ```

  每一步必须给出：
  - **这一步为什么是必要的**（一句话即可，回答"如果跳过这一步会怎样"）。
  - **这一步实际产出了什么成果**（引用对应 fact 在 §2.1 中的星级与一句话摘要）。
- 最后专门交代**结案那一步**：哪条 `intent`（`to=goal`）完成了项目，它是基于哪些 fact、用什么手法完成的。如果该 intent 有完整的 `complete.description`，要简短引用其中的关键判断依据。

#### 3.2 未产生实际成果的探索（一笔带过）

- 把所有"已结案但其产出 fact 没有进入 §3.1 主路径"的 intent，**集中归纳为一段简短叙述**（建议 100~200 字，最多 3~5 个要点）。**不要**为它们画 mermaid、不要展开证据、不要逐条编号。
- 句式建议：「曾尝试 X / Y / Z 等方向，分别因 〈失败原因 / 被绕过 / 不收敛〉 等原因未产出关键证据，相关意图为 `i0AA`、`i0BB`、`i0CC`，记录在图中以备审计。」
- 如果不存在这类无果探索，就写一句"无"。

---

### 四、报告总结

> 本段是**给最忙的读者看的最终摘要**：一张全景图 + 一句话结论。
> 不再重复成果表格——§2.1 已经按星级降序给出，请直接对照即可。

#### 4.1 项目全景图（完整 mermaid）

- 用一段 Mermaid 流程图（```mermaid``` 代码块）画出**完整项目图**，**包含所有节点**：
  - 节点：`origin`、所有产物 fact、`goal`，以及所有未产出 fact 的"无果意图"也用一个虚线节点表示（如 `i0AA[未产出]`）。
  - 边：每条已结案 intent 都用一条边，**边的标签**是 `<intent_id>` + 简短动作（如 `i003: 端口扫描`）。
  - 视觉建议：主成果路径上的节点用 `style fXXX fill:#dcfce7,stroke:#16a34a,stroke-width:2px`（绿色）加粗；无果意图节点用 `style i0AA fill:#fef3c7,stroke:#d97706,stroke-dasharray: 5 5`（黄色虚线）；`goal` 节点用 `style goal fill:#fee2e2,stroke:#dc2626,stroke-width:3px`（红色高亮）。
- 这张图必须能让读者**一眼看清"哪些路径产出了关键成果、哪些是死胡同"**。

#### 4.2 一句话结论

- 用**一句不超过 60 字的中文**总结整个项目：「最终通过 〈关键路径〉 达成 〈Goal 摘要〉，核心证据为 `<fact_id>`。」

---

## 编写口吻

- 客观、克制、可审计。**不要**写营销式的"令人惊叹"、"史无前例"等空话。
- **不要**虚构任何图中不存在的 fact / intent / id。
- 引用 fact / intent / hint 时一律使用其原始 id。
- 保留所有数字、IP、端口、URL、参数、错误码的精确值。
- 优先级判断要**保守**：宁可把一个边界 fact 标 P1 而不是 P0，避免重点摊薄。
